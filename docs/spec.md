# Smart Mail Dashboard — Спецификация проекта (spec.md)

## 1. Обзор системы
**Smart Mail Dashboard (Executive Notes AI Triage)** — локальная система автоматического сбора, интеллектуального триажа и визуализации входящей электронной почты руководителя из клиента Lotus Notes. 
Проект реализует парадигму *Spec-Driven Solo Development* и предназначен для запуска в изолированном локальном окружении с обращением к внешним API LLM (DeepSeek / Gemini).

## 2. Архитектура и стек технологий
Система разделена на три логических слоя:
1. **Frontend (UI/UX)**: Single Page Application (SPA), реализованное в едином файле `index.html` без внешних зависимостей. Использует Vanilla JS и CSS3.
2. **Backend (Логика и Интеграция)**: Python 3.x скрипт (`notes_gemini.py`), реализующий REST API через `http.server`. 
3. **Провайдер данных (Notes COM)**: Взаимодействие с почтовой базой осуществляется через `win32com.client` (Lotus.NotesSession).
4. **AI Модуль (Триаж)**: Интеграция с REST API LLM (по умолчанию DeepSeek API, поддержка Gemini) для суммаризации и приоритизации контента.

## 3. Структура файлов проекта
* `notes_gemini.py` — Точка входа, HTTP-сервер, бизнес-логика (парсинг COM, вызовы AI).
* `index.html` — Веб-интерфейс дашборда (HTML/CSS/JS).
* `set.ini` — Конфигурация приложения (API ключи, списки руководства E_TOP/E_DIR, сетевые параметры).
* `promt-get-post.txt` — Системный промпт для LLM (разбор входящей почты), содержит правила классификации и плейсхолдеры для инъекции данных.
* `promt-chat-post.txt` — Системный промпт «Чата по почте» (свободный вопрос по выжимке, возврат JSON `answer`/`refs`).
* `digest_template.txt` — Шаблон AI-сводки по всему потоку.
* `dashboard_data.json` — Локальная кэш-база писем, генерируемая после обработки AI.
* `work_state.json` — Отметки отработки письма (new / wip / done), живут отдельно от Notes и переживают пересбор.
* `seen_mail.json` — Журнал показанных писем для режима «новое с прошлого сбора».

## 4. Ключевые алгоритмы и Workflows

### 4.1. Сбор писем (Fetch Phase)
1. Инициализация COM-объекта `Lotus.NotesSession`.
2. Подключение к базе данных пользователя (поиск MailServer и MailFile из окружения).
3. Поиск писем по дате (`DeliveredDate >= [Date]`).
4. Извлечение метаданных: Универсальный ID (UNID), Отправитель (имя + email), Тема, Текст тела письма (очищенный от лишних пробелов, обрезанный по `max_body_chars`), статусы (Прочитано, Отвечено).
   - Email отправителя извлекается из полей Notes (`INetFrom`, `InternetFrom`, `InternetAddr`, `InternetAddress`, `Originator`, `From`) через функцию `extract_sender_email()` и сохраняется в поле `senderEmail`.
5. Формирование базового массива писем.
6. **Автоматическое сопоставление ФИО → email**: функция `resolve_names_to_emails()` по спискам `E_TOP` / `E_DIR` находит email-адреса среди собранных писем и сохраняет их в `e_top_emails` / `e_dir_emails` (секция `[TAGS]` файла `set.ini`). Ненайденные ФИО повторно проверяются при следующем чтении почты.

### 4.2. Интеллектуальный триаж (AI Triage Phase)
1. Сборка JSON-payload из массива писем (каждое письмо включает поле `email`).
2. Инъекция списков E_TOP и E_DIR (из `set.ini`) + списков почт `e_top_emails` / `e_dir_emails` в шаблон `promt-get-post.txt`.
3. Синхронный POST-запрос к API LLM с жестким требованием вернуть строго валидный JSON.
4. Парсинг ответа AI (поиск массива `emails`) и обогащение исходного массива:
   - **Приоритет** (`priority`/`criticality`): поддержка числовых значений (1–3) и строковых форм ("P1", "High priority", "срочно", "высокий", "средний" и т.д.), нормализация в диапазон 1–3.
   - **needsReply**: извлекается из булева поля ИЛИ из строки `action_type`/значений "нужен ответ", "да", "yes", "true", "требует ответа".
   - **summary** → запись в `threadMessages[0].text`.
   - **suggestedReply**: AI-рекомендованный ответ (поля `suggested_reply` / `suggestedReply`) сохраняется в `suggestedReply`.
   - Если `action_type == "Отвечено"` → проставляется `isReplied = True`.
   - Очистка markdown-код-блоков (```json ... ```) перед парсингом; ошибки парсинга JSON логируются и пакет пропускается (`continue`).
5. Сохранение обогащенных данных в `dashboard_data.json`.

### 4.3. Обратное взаимодействие (Action Phase)
* **Смена статуса прочтения**: POST `/api/mark-read` с `{ unid, is_read }` (или `{ unids, is_read }` — пакетно для цепочки) → COM `MarkRead()` / `MarkUnread()`; возвращает результат по каждому письму.
* **Смена состояния отработки**: POST `/api/set-state` с `{ unid, status, mark_read }` (или `{ unids, status, mark_read }`) → `set_work_states()`; `mark_read: true` при «Отработано» проставляет метку прочтения.
* **Переход в Notes**: ссылка `notes:///[ReplicaID]/0/[UNID]` открывает клиент Lotus Notes.
* **Ответить на письмо**: POST `/api/reply` с `{ unid, text }` → функция `create_notes_reply()` создаёт черновик в Notes (заполняет `SendTo` (отправитель исходного), `Subject` с префиксом "RE:", `Body` текстом ответа; `Save(True, True)` без отправки). Возвращает ссылку `notes://` на черновик.
* **Сохранение настроек**: POST `/api/save-settings` с `{ e_top, e_dir, ..., auto_done_days }` → сохранение ФИО и параметров в `set.ini`, пересчёт `e_top_emails`/`e_dir_emails` по кэшу `dashboard_data.json`, возврат актуальных почт.
* **Баланс DeepSeek**: GET `/api/balance` → запрос `{base_url}/user/balance` с ключом API, возвращает остаток средств (валюта, всего, бесплатно, пополнено).

### 4.4. Цепочки писем (Threading)
Письма одной темы (например `HA: >>: [#2026-8607411]: Обращение в поддержку HRlink` и ответы) объединяются в **цепочки** по ключу темы ([`thread_key()`](../notes_gemini.py)):
1. При сборе [`group_threads()`](../notes_gemini.py) проставляет `threadKey`, `threadSize`, `threadLatest`, `threadRoot` — голова цепочки (первый элемент, самое свежее письмо ветки).
2. В UI цепочка **свёрнута по умолчанию** — видна только голова; разворачивание показывает вложенные письма ([`chainHTML()`](../index.html)).
3. **Наследование пометок** ([`chainMembersOf()`](../index.html)): пометка первого элемента (голова) применяется ко **всей ветке** (отработка и прочтение); пометка вложенного письма — **только ему**.
4. Пакетная запись идёт одним вызовом `/api/set-state` / `/api/mark-read` с массивом `unids`.

### 4.5. Чат по почте (Chat)
Свободный вопрос по собранному потоку:
1. UI отправляет `POST /api/ask` с `{ question, history }` (история — последние ходы диалога).
2. [`answer_question()`](../notes_gemini.py) строит **сжатую выжимку** [`compact_index()`](../notes_gemini.py): до 200 писем по важности, тела — у 60 важнейших (180 символов).
3. System-промпт из [`promt-chat-post.txt`](../promt-chat-post.txt) подставляет выжимку в `[[EMAILS_PAYLOAD]]`; модель обязана вернуть JSON `{"answer", "refs"}`.
4. `refs` фильтруются до существующих id (до 10); в UI они становятся кликабельными и открывают письмо.

### 4.6. «Отработать все» (Bulk Done)
Кнопка в шапке дашборда ([`doneAllOld()`](../index.html)):
1. Читает `[UI] auto_done_days` из `set.ini` (по умолчанию 1 день) — сколько дней «оставить».
2. Помечает отработанными (`done`) все письма **старше** этого срока, **кроме писем «В работе»** (`wip` — остаются не отработанными).
3. Запись — пакетной `/api/set-state`.

### 4.7. Сводка без отработанных
[`build_digest()`](../notes_gemini.py) исключает из AI-сводки письма `workState == "done"` — сводка строится только по активным (`new`/`wip`); если активных нет, сводка не собирается.

## 5. Правила разработки для AI (Developer AI Rules)
*При внесении изменений в проект, AI-ассистент обязан соблюдать следующие правила (закреплено политикой разработки):*
1. **Анализ сбоев**: При исправлении ошибок (включая сбои I/O, COM-ошибки) подробно раскрывать первопричину сбоя и механику работы предложенного исправления.
2. **Рефаторинг**: Тщательно проверять сохранение логики. Никакая часть алгоритмов, метрик или расчетов не должна быть потеряна или "оптимизирована" в ущерб смыслу.
3. **Строгость контекста**: Опираться исключительно на предоставленные файлы. Запрещено выдумывать сущности, переменные, пути, URL, функции и архитектуру. 
4. **Уточнения**: Если параметров недостаточно, остановить генерацию и вывести: *"Для генерации ответа необходимы данные: [перечень]"*.
5. **Формат инструкций**: Инструкции по настройке ОС, ПО, сервисов выдавать только в виде готового к запуску кода (CLI, PowerShell, Bash, .reg, конфиги). Минимизировать шаги через GUI.
6. **Трассировка изменений**: При изменении кода явно фиксировать: 1) ЧТО изменено, 2) ПОЧЕМУ изменено.

## 7. Известные проблемы (Known Issues / Tech Debt)
- [ ] **Блокировка потока (Thread Locking):** Метод `do_POST` сервера `http.server` синхронный. Во время AI-триажа сервер не принимает другие запросы (костыль `ANALYSIS_LOCK`).
- [ ] **Безопасность Lotus Notes:** Если клиент заблокирован (ждет пароль), COM-интерфейс зависает.
- [ ] **Ошибки сопоставления ФИО (Bug):** Алгоритм `resolve_names_to_emails()` не всегда находит почту по ФИО из списков DIR, требуется отладка.
- [ ] **Хрупкость парсинга JSON:** Риск сбоя, если AI вернет markdown с пояснительным текстом внутри JSON-строки, несмотря на regex-очистку.
- [ ] **COM-изоляция:** Требуется изолировать вызовы `win32com.client.Dispatch` в рамках COM Apartment (`pythoncom.CoInitialize()`).
- [ ] **Чат ограничен выжимкой:** Модель видит не все письма, а до 200 по важности (тела — у 60). Вопрос по письму вне выжимки может не получить точного ответа.
- [ ] **Баланс зависит от прокси:** `GET /api/balance` работает только если `base_url` поддерживает `GET /user/balance`; для сторонних прокси возможна ошибка 404/403.
